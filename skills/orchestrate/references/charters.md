# Charters and registration

Read this reference when an authority home lacks a compatible registry or charter, a new orchestrator is proposed, or a meta experiment is applied.

A registry entry identifies a short action-oriented charter id, charter path, registration state, programme discovery, read and write resource claims, concurrency pools, permitted Ask Matt routes, and adoption authority. A charter defines purpose, completion, controls, evidence, and handoffs without live programme state.

An instance is `charter_id + programme_id`. Multiple instances may run when their registered write claims and capacity permit it. Draft or unregistered charters are read-only and proposal-only.

Meta observation requires bilateral registration: the control plane records the target and the target authority opts into the named meta charter and evidence scope. An experiment assignment must fit the target's declared tuning envelope and remains fixed for one work unit. Foundational authority, safety, tracker ownership, and mutation surfaces are not tunable.

Bootstrap reuses existing tracker and policy conventions. Propose only the missing registry, charter, pointer, or claim. Adoption ends when the exact change is reviewable; the root does not register or install it.
