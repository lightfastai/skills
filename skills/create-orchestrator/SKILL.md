# Create orchestrator

Interview the user one decision at a time. Produce an unregistered charter; registration is a separate adoption.

## Locate authority

Identify the domain being advanced and the authority home that owns it. A meta-orchestrator improves orchestration capability itself; cross-repository scope alone does not make an orchestrator meta.

Choose a short action-oriented name that says what the user asks it to do.

Completion: the authority home, level, name, and purpose are unambiguous.

## Define the charter

Resolve:

- programme identity and durable tracker source;
- completion boundary;
- read and write resource claims;
- concurrency pool and ceilings;
- permitted Ask Matt routes;
- evidence, gates, recovery, and handoffs;
- controls that are fixed and, when applicable, the meta tuning envelope.

Keep live tickets, tasks, branches, pull requests, blockers, and next actions out of the charter.

Completion: every requested effect maps to an authority and resource claim, and every terminal state is checkable.

## Test conflicts

Compare the draft with registered charters and active claims. Test at least ambiguous selection, overlapping writers, task interruption, out-of-authority work, and completion. A draft remains inspection- and proposal-only.

Completion: conflicts are resolved in the draft or reported as exact adoption blockers.

## Deliver

Return the draft charter, registry entry, affected pointers, conflict results, and bounded adoption sequence. Stop before registration, tracker creation, installation, or programme mutation.
